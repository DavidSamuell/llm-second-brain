## Decisions (not covered by the spec)
Full rationale for each is in `tasks/plan.md` under the D-number. This list is only the index. Reversible = can be changed after release without migrating data or breaking clients.

- [T5] D1: Python 3.13, uv workspace, ruff, mypy --strict, pytest, argparse CLIs. Why: one lockfile, no extra CLI dependencies. Reversible: yes.
- [T10] D3: all kit containers run as `${PUID}:${PGID}`, the same ids as Ignis, with a single uvicorn worker. Why: shared file ownership in `/vault`, and rate-limit and lease state live in memory. Reversible: yes.
- [T10, T29] D5: ingress is chosen by setup writing `COMPOSE_FILE` (base + `ingress/<name>/compose.yml`) into `.env`; git-sync and agent-runner use compose `profiles`. Why: compose `include:` has interpolation bugs, and plain `docker compose up` must keep working. Reversible: yes.
- [T7] D6: the advisory lock is `flock(2)` on `/data/locks/vault.lock`, with the holder's name in `vault.owner`. Why: works across containers, interoperates with `flock(1)`, and is released when a process crashes. Reversible: yes until git-sync ships; after that both sides must change together.
- [T7] D7: `version` is the lowercase hex sha256 of raw bytes, `null` when the file doesn't exist; writes use a same-directory temp file + `os.replace`. Why: atomic and independent of mtime. Reversible: **no** once clients store versions.
- [T6] D8: `--folders` limits read, list, search, and write, using case-sensitive prefix matching. Reversible: yes.
- [T6] D9: the maintainer comes from the file **on disk**, not from the incoming content; a new file only has to pass `write.allow`. Reversible: yes.
- [T10] D10: errors are `ToolError` with JSON `{code, message, details}` and a fixed list of codes. Reversible: **no** once agents and skills parse the codes.
- [T17] D11: `heading` accepts the bare text or the full `## line`, matching exactly one heading; `insert_after` inserts directly below the heading line. Reversible: no (it changes where content lands).
- [T10] D13: non-UTF-8 files are returned as `content_base64` + `mime`; write tools accept text only. Reversible: yes.
- [T20] D14: leases are stored in `/data/state.db`, a file not listed in §4. Submitted sources are named `raw/<date>-<slug>.md`. Reversible: yes.
- [T18] D15: the review queue is Obsidian tasks in `_system/review-queue.md` with `#review` / `#review/high` tags and `^rq-<id>` block ids. Reversible: no, without migrating existing items.
- [T9] D16: tokens are `vmcp_` + 32 bytes, stored as sha256 hashes; `--expires` defaults to `90d`, and `never` must be explicit. Reversible: the default yes; the token format no.
- [T24] D17: a subclass of FastMCP `OAuthProvider` on `tokens.db`; opaque tokens (access 1 h, refresh 30 d with rotation); scopes `vault:read` / `vault:write`. Reversible: partly; changing scope names breaks existing grants.
- [T25] D18: authlib for upstream login; GitHub only via its verified-email API; upstream tokens are discarded. Reversible: yes.
- [T21] D19: rate-limit counters live in memory, so `writes_per_day` resets when vault-mcp restarts. Reversible: yes.
- [T8] D20: every tool call is audited, reads included; no log rotation in v1. Reversible: yes.
- [T14] D23: FTS5 with `unicode61 remove_diacritics 2` and no stemming; user terms are quoted; `read.deny` paths are never indexed. Reversible: yes (reindex).
- [T8] D24: curated regex rules from gitleaks' high-confidence set, no entropy rules, and no allowlist bypass. Reversible: yes.
- [T8] D25: the webhook payload shape is picked from the URL host (Slack, Discord, or generic). Reversible: yes.
- [T23] D26: the watcher monitors peers through `/health` and heartbeat files, with no Docker socket. Reversible: yes.
- [T6, T29] D27: `vault-mcp.yaml` is generated from `vault-mcp.example.yaml` and gitignored; changes need a restart. Reversible: yes.

This fits the spec: vault-mcp's write path takes the shared §6.6 lock for every runner write, and §9 offers the filesystem as an option, not a requirement. Why: see the T2 surprises below. This is the fallback the plan named before T2 started. Reversible: yes, until clients store the endpoints.
- [T3] D21 step order fixed: make `post.blob`, the temp file and `txn.json` durable → read the current file → make `pre.blob` + `pre.json` durable → re-read and compare → `os.replace`. A changed file at the compare is `conflict` for tools with `base_version`, and a redo for `append`/`insert_after`. Why: the T3 measurements below. Defaults kept: `HISTORY_ACK_TIMEOUT=5s`, debounce 5 s / 60 s, heartbeat stale after 30 s. Reversible: yes.
- [T10] `get_schema` serves `AGENTS.md` to every credential, whatever its `--folders`, because it is the vault's rulebook. `list("")` lists the vault root, and a folder outside a credential's scope still shows when it leads to a scoped folder (e.g. `wiki/` for scope `wiki/concepts/`). Reversible: yes.
- [T10] stdio mode re-verifies `VAULT_MCP_TOKEN` on every tool call, so revoking it takes effect without restarting the agent's server process. Reversible: yes.
- [T10] `vault-mcp serve` listens on `0.0.0.0:8082` inside the container; the host side is published only on `${BIND_ADDR}` (default 127.0.0.1). The BIND_ADDR warning is printed at startup when it isn't loopback (checked against the container). Reversible: yes.
- [T13] History records every vault file except `.git/`, `.trash/`, `.obsidian/workspace*`, `.obsidian/cache` and vault-mcp temp files. So Obsidian config under `.obsidian/` (app.json, plugin settings) is versioned too. Why: config changes are recoverable that way, and D22 only excluded layout and cache. Reversible: yes.
- [T13] Attribution: an fs event that arrives while `git-sync` holds the vault lock marks that path's debounced burst as `git`; other events are `web`; startup and periodic scans record `unknown`. The watcher's `/health` runs on port 8083 inside the compose network only and reports unhealthy if the heartbeat is stale. Reversible: yes.
- [T16] `append` on a missing file returns `not_found` (create with `write`), so a typo in the path can't create a stray page. `append` starts the text on a new line if the file doesn't end with one. Reversible: yes.
- [T16] For write tools the durable `ok` audit line is written by the writer itself, under the same id as the history version, so a successful write has exactly one audit line; refusals and failures are logged by the server wrapper. The locked part of a write runs in a worker thread so its fsyncs don't stall other requests. Reversible: yes.
- [T18] `review_queue_add` is open to every write credential regardless of its `--folders` (the queue is how agents ask about pages they can't edit), but the `page` must be readable by the credential, so denied pages can't be named. Field text is flattened to one line and `[[`/`]]` are removed so an item can't break the task list or inject links. Reversible: yes.
- [T18 review fix] D8 tightened: MCP tools, history and the search index ignore every path that goes through a symlink, including in-vault ones. A symlinked alias would otherwise carry its own path's permissions to the target. Vaults that rely on symlinks lose MCP access to those paths (the real paths still work). Reversible: yes, by checking policy on the canonical target instead.
- [T19] Wikilinks resolve the way Obsidian does: by path suffix, ties going to the linking page's folder, then the shortest path. Rewritten links keep their style (bare name, full path, `.md` suffix, alias, heading, embed) and fall back to the full path if the bare name would become ambiguous. The move scan includes hidden Markdown pages (a link there blocks the move, counted without its path) but not `.trash/` or `.git/`. Link rewrites in a move skip the secret scan: they only change link targets. Reversible: yes.
- [T19] If a file in a move group changes while the group is being applied, vault-mcp stops before overwriting it, returns `conflict` listing applied / not-applied files, and leaves the entries for vault-watcher, which classifies them and sends a `move_partial` alert. The vault can be left with a half-done move for a human to finish; overwriting the browser save was the alternative. Reversible: yes.
- [T20] Leases are in `/data/state.db`. A claim checks, renames and records the lease under the vault lock. A file left in `raw/_processing/` without a lease (a crash between rename and lease) is returned to `raw/` once older than the default 30-minute TTL. `ttl_minutes` may be 1–1440. Renames to an existing name get a `-2`, `-3`… suffix. The sweeper acts as a system actor (`lease-sweeper`) recorded in the audit log. Reversible: yes.
- [T21] Rate limits are per credential, kept in memory (they reset on a vault-mcp restart) and enforced on every MCP tool call. A write counts toward the request limit too. Refused calls are not counted, so retrying doesn't extend the window. `retry_after_s` is returned in the error details. The `rate_limit_repeated` alert is sent at most once per credential per hour. `ALERT_WEBHOOK` now reaches vault-mcp as well (compose + `Settings.alert_webhook`). Reversible: yes.
- [T22] The watcher scans every changed tracked file that is text, whatever its name (binary = NUL in the first 8 KiB or invalid UTF-8; no size cap, so large text files are scanned too), after every recorded change, including committed MCP writes. Findings are deduped forever by (path, rule, fingerprint) in `index.db` table `secret_findings`; deleting `index.db` re-reports open findings once. Each finding is reported at least once, in this order: alert, review item, audit line, dedupe row. vault-watcher appends review items itself (atomic replace, under the vault lock) and records them in history with the new source `system`. As with MCP writes, a browser save to the queue at the same moment could race this (D21 known limit). Reversible: yes.
- [T23] The monitor runs as a thread in vault-watcher (`MONITOR_INTERVAL_S`, default 60; e2e uses 2). Peers come from `MONITOR_PEERS` (`vault-mcp`, `ignis`). Heartbeats come from `MONITOR_HEARTBEATS`, checked only when the service's state directory exists under `/data`, and stale after 3 intervals. Disk checks cover `/vault` and `/data` at > 80 %. Alerts fire on the 3rd consecutive failure, once per outage, followed by an info-level `service_recovered`. vault-watcher can't check itself; its own compose healthcheck covers that. Reversible: yes.
- [T24] OAuth grant names are `oauth:<client name>-<6 chars of the grant id>`, not plain `oauth:<client_name>`. The active-name index is unique, and several people connect the same app. Reversible: yes.
- [T24] `vault-mcp oauth approve-code --scope` defaults to `read`; the admin passes `--scope write` explicitly. The consent page lets the person grant less than the code allows, never more. Codes are 10 Crockford base32 characters shown as `XXXXX-XXXXX`, case and dash insensitive, with O/I/L read as 0/1/1. They're valid 1 minute to 7 days (default 1 h), stored hashed, single use. Wrong codes: 5 per request, then it's dropped; 30 per 10 minutes server-wide, then all sign-ins pause. Reversible: yes.
- [T24] OAuth is on only when `MCP_OAUTH_ENABLED=true` **and** `MCP_OAUTH_ISSUER` is set. With no issuer, vault-mcp logs a warning and stays bearer-only, rather than refusing to start (local installs have no public URL). Reversible: yes.
- [T24] Token lifetimes: access 1 h; refresh 30 days rolling, rotated on each use. The grant's `expires_at` moves with the refresh token, so `token list` shows it expiring when unused. Revoking either token through RFC 7009 `/revoke` ends the whole grant. Reversible: yes.
- [T24] Registration: redirect URIs must be https, loopback http, or a private-use app scheme (not javascript/data/file, no fragment). At most 1000 clients; unused ones older than 7 days are pruned on each registration. DCR client secrets (confidential clients only) are stored in plain text in `tokens.db` (0600), because the SDK's client authenticator compares plain text; PKCE is still required. Reversible: yes.
- [T24] The kit's pages bind each authorization request to the browser that opened it: an HttpOnly, SameSite=Lax cookie on `/oauth`, plus a one-time CSRF token per form. Pages send `frame-ancestors 'none'`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer` and `no-store`. Every grant approval is audited (`oauth_consent`). Reversible: yes.

## Surprises (T24)
- FastMCP turns `invalid_grant` from the token endpoint into HTTP **401**, not 400 (the MCP spec requires 401 for invalid tokens). Tests assert 401.
- The SDK's RFC 7009 revocation handler requires a `client_secret` form field even for public clients (it is declared without a default). Public clients that omit it get 400 and nothing is revoked. Revocation through `token revoke` is unaffected; we kept the SDK handler and document the quirk.
- [T25] D18 named authlib. vault-mcp instead uses `httpx` for the code exchange and `joserfc` (authlib's own JOSE backend; `authlib.jose` is deprecated in 1.9) to verify ID tokens. That is one small dependency and no client framework. Upstream sign-in uses PKCE and an OIDC nonce; the authorization request id is the `state`. Reversible: yes.
- [T25] Microsoft sign-in requires `OAUTH_UPSTREAM_TENANT` (a tenant id or domain, never `common`/`organizations`/`consumers`). A multi-tenant login would accept any tenant's self-asserted email (the "nOAuth" class of bug). Inside that tenant, the `email` claim (or `preferred_username`) is trusted, because Entra ID doesn't send `email_verified`. Reversible: yes.
- [T25] Anyone who signs in upstream with an allowed email domain may grant `write`, but can narrow it to read on the consent page. An upstream provider without `OAUTH_UPSTREAM_ALLOWED_EMAIL_DOMAINS` refuses to start, so a misconfigured Google login can't admit every Google account. When an upstream is set, the approval-code form is turned off. Reversible: yes.
- [T28] The hardening code is `vault_watcher.ignis_harden` (CLI `vault-watcher harden-ignis`), not a loose `ignis/harden.py`. The ignis-init service reuses the vault-watcher image, so the code is type-checked, unit-tested and shipped in an image that is already pinned. Read-write `data.json` mounts for `writable_data` plugins come from a generated `compose.plugins.yml` (`harden-ignis --compose`); ignis-init refuses to run if the allowlist and the mounted list differ. `IGNIS_PLUGIN_BASE_URL` (default `https://github.com`) exists so e2e can serve fake releases. Managed `.obsidian/app.json` and `templates.json` are reset on every start; other `.obsidian` files are left alone. `${DATA_PATH}/ignis-plugins` must exist before `compose up` (setup creates it), otherwise Docker creates it as root. Reversible: yes.
- [T29] `.env.example` adds `VAULT_NAME`, `PUID`/`PGID` (setup writes `id -u`/`id -g`), `OAUTH_COOKIE_SECRET` (caddy; setup generates it), `OAUTH_UPSTREAM_ISSUER`/`OAUTH_UPSTREAM_TENANT`, `AGENT_RUNNER_TOKEN`, `MONITOR_INTERVAL_S`, `HISTORY_ACK_TIMEOUT`, `IGNIS_PLUGINS_FILE` and the D5 `COMPOSE_*` values. The default `INGRESS` is `local`, not §13's `cloudflare`, so a first run works without a domain. Setup refuses `example.com` hostnames for public profiles. An existing vault without AGENTS.md is adopted only with consent (`--adopt` or the prompt); adoption never overwrites. Reversible: yes.
- [Checkpoint D] Security review fixes (`docs/reviews/2026-11-10-oauth-security-review.md`):
  - vault-mcp now serves `/authorize` (SDK handler, wrapped so errors never redirect to a registered URI) and `/revoke` (own RFC 7009 handler: public clients need no secret) instead of the SDK routes.
  - Pending sign-ins are capped at 1000 server-wide and 20 per client. The PKCE challenge must be 43 characters; `state` and `resource` are at most 512.
  - Registration evicts the oldest unused client when it reaches the cap.
  - Approval-code failures only alert (`oauth_code_guessing`) above 30 in 10 minutes.
  - Refresh-token reuse is audited and sends a high alert.
  - Google accounts must carry `hd`, so only Workspace accounts get in. Entra accepts a tenant given by domain: its discovered GUID issuer is accepted.
  - Known remainders for SECURITY.md: Entra guest accounts inside the tenant (restrict with "assignment required" on the app); GitHub verified emails outlive the mailbox (prefer approval codes or an org IdP); approval codes are 50-bit sha256 hashes (a leaked tokens.db could crack a live code). Reversible: yes.
- [T32] check-exposure reports SKIP rather than FAIL where a check can't apply: no `CHECK_TOKEN`, OAuth disabled, no public address on the host, or `CHECK_SKIP=ignis-login` (an editor reachable only inside a tailnet the checking host belongs to). For `INGRESS=local` setup doesn't run it (there are no URLs); local.md documents a manual port probe instead. Reversible: yes.
- [T34] git-sync uses util-linux `flock` (Alpine's BusyBox `flock` has no `-w`). Commit requests are consumed once the commit lands; several requests in one cycle produce one commit named after the oldest. Pushing is paused (a `blocked` file, plus an alert) only when a rebase can't be resolved automatically. Reversible: yes.
- [T35] agent-runner mounts only `${DATA_PATH}/agent-runner`, `${DATA_PATH}/git-sync/requests` and the vault's `skills/` (read-only), not AGENTS.md: the agent reads the rules through `get_schema`, and setup creates those data folders so Docker never creates them as root. Claude Code may only use `mcp__vault__*` tools, so it can't read files around the policy. Commit requests are written only when `GIT_REMOTE` is set. The `ingest` prompt caps a run at `INGEST_MAX_SOURCES` (default 10). Reversible: yes.

## Surprises (things learned)
- The repo started with only `SPEC.md`, `README.md` (18 B), and a stock Python `.gitignore`, so there are no existing conventions to follow.
- Ignis expects vaults under `VAULT_ROOT=/vaults/<name>` (one sub-folder per vault), listens on 8080 internally, keeps its state in `/app/data`, and caches Obsidian in `/app/obsidian-app`. Source: https://ignis.thiefling.com/docs/server/deploy/
- Ignis doesn't enforce write protection and has no auth, but it has `WS_ORIGINS` for Origin allowlisting. Source: https://ignis.thiefling.com/docs/server/environment/
- [T1] An older `OBSIDIAN_VERSION` is **not rejected**. Ignis logs `… is older than this build's Obsidian 1.14.4; using 1.14.4.` and runs its pin, so §16.18 has to be checked from the `Obsidian (ready|already set up) (vX)` log line.
- [T1] Pinned image `nobbe/ignis@sha256:2049be7dfbbee5ee9fa5c0ae56efd8555ec57f2ac3275448b1c4318b8af49bb5` = Ignis monorepo 0.9.0 with Obsidian 1.14.4. The image env already includes `IGNIS_OBSIDIAN_PIN=1.14.4` and the label `com.thiefling.ignis.obsidian-version`.
- [T1] Obsidian's `app` is a global lexical binding, not a `window` property. `window.app` is `undefined`; a bare `app` works. Puppeteer's `page.evaluate` inside the omp browser runtime runs in an isolated world and can't see it, but CDP `Runtime.evaluate` can. This matters for the T38 Playwright nightly.
- [T1] Workspace layout is shared through the vault's `.obsidian/workspace.json`; mobile clients use `workspace-mobile.json`.
- [T1] Restricted mode (whether community plugins are on) is stored per browser in localStorage (`enable-plugin-<vault>`), not on the server.
- [T1] Docker creates a missing bind-mount target as `root`, even inside the vault. This happened with the plugins directory and left it unusable by Ignis afterwards. D28 now says `ignis-init` must create these paths first.
- [T1] Two people typing in one note at the same time: the last save wins, and the losing editor stays out of sync until its next save overwrites the other person's text.
- [T1] If a file is atomically replaced while someone is typing in it, the editor reloads from disk and drops the keystrokes it hadn't saved yet.
- FastMCP `OAuthProxy` keeps clients and tokens in its own encrypted key-value store and passes upstream tokens through, so it can't satisfy §6.3's single `tokens.db`.
